「Kubernetes 有自愈能力」几乎是所有教程的默认前提，但往下追问一层就不好回答了：

> 把节点杀掉之后，业务到底恢复了多久？恢复过程中丢了多少请求？

大部分资料只演示「Pod 被删了会自动重建」，这叫**功能验证**，不叫**能力评估**。毕设我想做的是后者。

## 自愈其实是三段链路

把它拆开，就会发现瓶颈通常不在你可能以为的那一段：

| 阶段 | 谁负责 | 典型耗时来源 |
| --- | --- | --- |
| 故障检测 | kubelet / node controller | 心跳超时、探针周期 |
| 决策调度 | scheduler / controller-manager | 调度排队、亲和性约束 |
| 实际恢复 | 拉镜像、挂卷、启动探针 | 镜像体积、PV 绑定、就绪延迟 |

例如节点失联，默认要等 `node-monitor-grace-period`（40s）才被判定 NotReady，再加上驱逐超时，一分钟就过去了。**这段时间业务是不是还能服务，取决于你有没有做多副本和反亲和。**

## 用 Chaos Mesh 制造可控故障

Chaos Mesh 的价值是让故障**可复现、可编排、可观测**，而不是靠人肉 `kubectl delete`。

我打算覆盖几类故障，从轻到重：

- `PodChaos` — pod-kill / container-kill，最轻，测单副本恢复
- `NetworkChaos` — delay / loss / partition，测网络抖动下的服务可用性
- `StressChaos` — CPU / 内存压力，测资源竞争下的调度表现
- `PodChaos` + 节点层面 — 模拟节点失联，测多副本与反亲和的真实效果

关键是**每次只动一个变量**，否则数据没法归因。

## 指标体系：不要只看平均值

这是我最想强调的一点。测恢复时间如果只报平均值，结论基本没有说服力——尾部延迟才是用户真正感受到的东西。

所以我打算采集：

- **RTO**：从故障注入到服务恢复的时间，同时给 **P50 / P95 / P99**
- **错误率**：故障窗口内的请求失败比例
- **请求丢失数**：绝对量，比百分比更直观
- **恢复抖动**：多次实验的离散程度，用来判断稳定性

```
一次实验 = 注入故障 → 持续压测 → 记录指标 → 恢复 → 观察 5 分钟
重复 N 次，取分布而不是单点值
```

## 实验环境

原来的方案是 MacBook + OrbStack + K3s，跑通之后发现两个问题：ARM64 和 x86_64 的镜像行为不一致，而且单机模拟节点故障不够真实。

现在改成在 Proxmox VE 上搭一套 6 节点的 kubeadm 高可用集群，节点之间可以真的关机、断网。这样故障才像故障。
