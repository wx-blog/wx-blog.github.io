写完几个 playbook 之后一定会遇到这个问题：同一套"装 nginx + 配虚拟主机 + 起服务"的流程，在三个项目里各写了一遍。Role 就是为这件事存在的——把任务、变量、模板、handler 打包成一个可复用的单元。

这篇从一个空骨架开始，把每个目录的职责捋清，重点是那个最经典的坑：`defaults` 和 `vars` 到底谁盖谁。

## 生成骨架

Role 有固定的目录约定，不用手建。用 `ansible-galaxy init` 生成：

```bash
mkdir -p roles
export ANSIBLE_ROLES_PATH=/project1/roles
ansible-galaxy init full_role --init-path roles/
```

`ANSIBLE_ROLES_PATH` 是告诉 Ansible 去哪找 role。设了它，playbook 里写 role 名就行，不用写全路径。

生成出来的结构是这样：

```text
full_role/
├── defaults/     # 默认变量（优先级最低）
├── files/        # 静态文件，copy 模块的源
├── handlers/     # 被 notify 触发的任务
├── meta/         # 依赖与元信息
├── tasks/        # 主任务列表
├── templates/    # Jinja2 模板，template 模块的源
├── tests/        # 测试 playbook
└── vars/         # 变量（优先级最高）
```

## 每个目录负责什么

**`tasks/main.yml`** 是入口。playbook 引用 role 时，Ansible 自动执行这个文件，其它任务文件要靠 `include_tasks` 引进来。

**`files/`** 放原样拷贝的文件，配合 `copy` 模块：

```yaml
- name: 主任务 - 拷贝静态文件
  ansible.builtin.copy:
    src: full_role_file.txt
    dest: /tmp/full_role_file.txt
  notify: Main handler
```

**`templates/`** 放 Jinja2 模板，配合 `template` 模块。模板里可以用变量、过滤器，渲染后再送到目标机：

```jinja
# templates/config.j2
# Configuration generated by full_role
hostname = {{ ansible_facts['hostname'] }}
extra_var_msg = {{ extra_var_msg | default('not set') }}
```

注意那个 `| default('not set')`——**变量可能没定义**，给个兜底值比让 playbook 报错友好得多。

## defaults 和 vars 谁盖谁（重点）

这是 Ansible 里最常考的优先级问题，答案是：

| 目录 | 优先级 | 能不能被外部覆盖 |
|---|---|---|
| `defaults/main.yml` | **最低** | **能**，随便覆盖 |
| `vars/main.yml` | **很高** | **基本不能**，几乎只有 `--extra-vars` 能盖过它 |

所以选哪个不是风格问题，是语义问题：

- 这个值是"默认值，别人多半要改"→ 放 `defaults`
- 这个值是"这个 role 内部必须成立的前提"（比如内部约定的路径）→ 放 `vars`

判断错了会出现很诡异的现象：你在 playbook 里传了变量，但它没生效——因为它在 `vars` 里被钉死了。

:::warn
把"希望可配置"的变量放进 `vars/`，是被覆盖不生效的头号原因。养成习惯：**能放 `defaults` 就放 `defaults`**。
:::

## 从外部文件加载变量

`defaults/` 和 `vars/` 里的 `main.yml` 是自动加载的。如果变量太多、想拆成多个文件，就要显式 include：

```yaml
# tasks/main.yml
- name: 加载额外的 defaults 变量
  ansible.builtin.include_vars:
    file: "{{ role_path }}/defaults/extra_defaults.yml"

- name: 加载额外的 vars 变量
  ansible.builtin.include_vars:
    file: "{{ role_path }}/vars/extra_vars.yml"

- name: 加载 meta 目录下的变量
  ansible.builtin.include_vars:
    file: "{{ role_path }}/meta/meta_extra.yml"
```

`{{ role_path }}` 是 role 自己的根目录，用它能写出相对 role 的路径，role 被挪到别处也不会断。

:::note
`include_vars` 加载的变量，**优先级由加载方式决定**，不会因为文件放在 `defaults/` 目录下就自动变成"默认级"。目录名在这里只是文件夹名，不产生语义。这是个容易被误解的点。
:::

## handler 与 notify

handler 是被 `notify` 触发的任务，典型用途是"配置改了才重启服务"：

```yaml
# handlers/main.yml
- name: Main handler
  ansible.builtin.debug:
    msg: "Main handler triggered"

- name: Include extra handlers
  ansible.builtin.include_tasks: extra_handlers.yml
```

在任务里挂上：

```yaml
- name: 主任务 - 渲染配置文件
  ansible.builtin.template:
    src: config.j2
    dest: /tmp/full_role_config.cfg
  notify: Extra handler
```

两个关键机制要说清楚：

**其一，`changed` 才触发。** 任务的执行结果是 `ok`（没有变化）时，`notify` 不会触发。这正是它的价值——配置文件内容没变就不重启服务。

**其二，handler 在 play 末尾统一执行，而且只执行一次。** 即使有三个任务都 notify 了同一个 handler，它也只跑一次。这个行为是刻意的（避免服务被重启三遍），但也意味着**handler 的执行时机和你写的位置无关**——别指望它立刻生效。

## 拆分任务

任务多了就拆文件，用 `include_tasks`：

```yaml
- name: 引入额外的任务
  ansible.builtin.include_tasks: extra_tasks.yml
```

`include_tasks` 是**运行时**动态引入，引入的文件内容会出现在执行输出里（`included: .../extra_tasks.yml`），排查问题的定位更直观。

## 测试与运行

骨架里自带 `tests/`，写一个最小 playbook 就能跑：

```yaml
# tests/test.yml
- name: Test full_role
  hosts: node1
  roles:
    - full_role
```

跑之前先做语法检查，这一步能省很多往返：

```bash
ansible-playbook roles/full_role/tests/test.yml --syntax-check
```

正式执行：

```bash
ansible-playbook roles/full_role/tests/test.yml
```

执行输出里每个任务都带 role 名前缀，一眼能看出是谁干的：

```text
TASK [full_role : Main task - copy static file] *******
TASK [full_role : Main task - template configuration] *
TASK [full_role : Task from extra_tasks.yml] **********
```

最后那个 `PLAY RECAP` 是验收重点，`ok=9 changed=0 failed=0` 表示全部到位且没有意外变更。

## 踩坑清单

| 现象 | 原因 | 处理 |
|---|---|---|
| 传进去的变量没生效 | 变量写在了 `vars/` 里被钉死 | 挪到 `defaults/` |
| handler 没执行 | 任务结果是 `ok` 不是 `changed` | 确认内容真的变了，或检查 `notify` 名字拼写 |
| role 找不到 | 没设 `ANSIBLE_ROLES_PATH` | 设环境变量，或写全路径 |
| 模板里变量未定义报错 | 变量可能为空 | 加 `\| default('...')` 兜底 |
| `include_vars` 的变量优先级不符预期 | 误以为目录名会决定优先级 | 记住：目录名不产生语义 |

## 速查

```bash
ansible-galaxy init <role> --init-path roles/   # 生成骨架
ansible-playbook <playbook> --syntax-check      # 先查语法
ansible-playbook <playbook>                     # 执行
```

Role 的本质就是"把一堆约定俗成的文件放在约定的位置"。搞清楚 `defaults` 与 `vars` 的区别、handler 的触发时机这两点，剩下的都是体力活。
